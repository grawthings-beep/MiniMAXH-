# Character R2V Quality 2x

## 何が変わるか

キャラ画像1枚を外見の資料として渡し、冒頭の構図・動き・最後の見せ場はプロンプトで指定します。
画像は `MiniMaxH3ReferenceToVideo.ref_images` に接続されます。first_frame、last_frame、
キーフレームとしては接続しません。参照画像が自動的に冒頭へ挿入される設計ではありません。
ただしモデルが似た構図を生成する可能性はあり、意図通りの演出・完全なキャラ保持を保証しません。

既存の01/02/03のJSON・モデル・LoRA設定は変更しません。04は独立した追加ワークフローです。
一般的なキャラ演出の基準として、04には追加LoRAもTurboも近似キャッシュも使いません。
画像・プロンプトを外部サービスへ送信しません。プロンプト生成APIも使いません。
RunPodのGPU/ディスク料金は従来どおり発生します。

## RunPodでの有効化

この機能を含む新しいDocker imageへ切り替えたうえで、既存環境変数へ追加します。

```text
H3_CHARACTER_R2V=1
```

`MODEL_MANIFEST=/opt/minimax-h3/manifests/minimax_h3_i2v_upscale.json` はそのままで使えます。
起動時に既存manifestと `minimax_h3_all.json` のモデル一覧を重複なしで統合します。
通常の並列Xet/再開可能aria2フォールバック・サイズ/SHA256検証をそのまま使用し、
統合後の容量でpreflightします。共有Qwen、VAE、upscalerを別プロセスで重複取得しません。
ユーザーが別HF repo/revisionのmanifestを指定していた場合は、黙って置換せず停止します。

追加モデル:

```text
Comfy-Org/MiniMax-H3
revision: fd70b39279d1ae6eb214c903f53e1bec3af19a77
diffusion_models/minimax_h3_ref2va_pruned_int8_convrot.safetensors
size: 20970379616 bytes
SHA256: 9255f52b6677845ad238f20dfaafa94727053694127ab7f255c048f0f9365779
```

合計の基本モデル容量は63,508,026,812 bytes（約59.15GiB）。既存LoRA、モザイクモデル、
Docker image、出力動画、ダウンロード中の一時領域は別です。従来の120GBコンテナディスクを
出発点にし、生成結果の保存分も確保してください。永続ストレージは必須ではありません。
重みはDocker build時には取得しません。

`H3_CHARACTER_R2V=0`（既定）なら追加モデルは自動取得せず、従来3本だけを配置します。
既に手動設定したMODEL_MANIFESTにref2vaが含まれる場合は、その設定に従って取得します。
必要ファイルのダウンロード/検証に失敗した状態ではComfyUIを起動しません。

## UI操作

1. `04_MiniMax_H3_Character_R2V_2x` を開く。
2. 左端の **キャラ画像** へ1人のキャラの画像をアップロードする。
3. **演出を入力** ノードの `direction` を編集する。画像の見えない部分を想像で長く説明するより、
   冒頭に何を見せ、途中で何が変わり、最後に何を見せるかを書く。
4. `identity_notes` へ、残したい顔・目・髪・衣装の特徴を追加する。
5. 初回は5秒・0.4MP・25 steps・seed固定で生成する。
6. 顔と構成が良い候補を見つけてから、出力解像度や尺を一つずつ上げる。

`direction` モードは入力を公式の6見出し構成へ整形するだけです。
日本語から英語への翻訳、参照画像の解析、LLMによる脚本の自動補完はしません。
英語の映像指示を推奨します。台詞は話させたい言語で指定してください。
`full_prompt` モードでは `direction` 欄の全文を無加工で送ります。
その場合は `identity_notes` / `soundscape` / `music` 欄は使いません。

尺はH3の17k+5フレームへ切り上げます（24fps）：5秒→124フレーム/5.17秒、
7秒→175フレーム/7.29秒、10秒→243フレーム/10.13秒。
プロンプト内の時刻は強制拘束ではありません。初期サンプルは「前半/中盤/終盤」で記述します。
full_promptへ絶対時刻を書く場合は、尺変更時に自分で合わせてください。

## 画質とメモリの調整

| 段階 | 設定 | 確認点 |
|---|---|---|
| 動作・演出チェック | 0.4MP / 5秒 / 25 steps / 参照長辺1024 | キャラ、顔、オチ、音声が成立するか |
| 中間品質 | 0.6MP / 同じ尺・seed | 線・目・衣装の細部とメモリ余裕 |
| 最終候補 | 0.98MP（縦長は768×1344）/ 25 steps | 元解像度の細部、連続フレームの安定性 |
| 尺を伸ばす | 品質比較後に7秒などへ | 秒数と解像度を同時に上げない |

初期0.4MPは最大品質設定ではありません。2xは縦横を2倍にするため、画素数は4倍です。
Real-ESRGANは元の動き・顔の誤りを直す機構ではなく、フレームごとの拡大です。
時間方向のちらつきが出る場合は、upscalerをbypassして元動画とも比較してください。

参照画像は専用ノードで長辺1024px以内、H3の32px格子へ縮小します。
切り抜きはせず、縦横比の小さな丸め誤差は生じます。小画像の拡大はしません。
native R2Vの `ref_image_size=max` は、この制限後の画像を使用します。
巨大な2048px参照を無条件に送る構成ではありません。1024は実機で最適と証明した値ではなく、
試験開始用の上限です。OOM時は長辺768、出力0.3–0.4MP、5秒へ戻してください。
`match` へ変更すると参照が生成画素数程度までさらに縮小されます。

モデル退避→ネイティブタイルVideo VAE→2x→既存CPUモザイク→MP4の順序です。
モザイクのON/OFFは最終出力側の `enabled` で変更でき、参照画像にはかかりません。
参照のVAE encode・Qwen・サンプリング・upscaleもメモリを使うので、decode対策だけで
OOMを完全に防げるわけではありません。32GB/48GB/24GBのどれにも生成成功を保証しません。
I2VとR2Vを交互に実行すると、ComfyUIのキャッシュに両モデルが残りシステムRAM負荷も増えます。
実機比較は各モードを再起動後に単独で行い、その後に連続生成テストをしてください。

## キャラ保持と演出を評価する

- キャラの顔と衣装が十分読める1枚を使う。複数コマのキャラシートはまず1コマへ分ける。
- 見えていない背面へ大きく回転させるなど、参照にない情報を同時に要求しすぎない。
- 「美少女化」「巨大な目」など元絵と競合するスタイル指定を増やさない。
- 最初は1場面・1キャラ・1回の見せ場。長文にするより、画面に映る変化を具体的に書く。
- 同じseedで変更点を1つずつ比べ、さらに複数seedでも確認する。良い1本だけで一般化しない。
- 最終表情だけでなく、顔が現れる直前/途中、目の形、衣装の変化、ちらつきも確認する。
- 画像を完全に隠す開始画面とキャラ保持が両立しない場合は、冒頭構図画像を別途作るI2Vが代替。
  R2Vが全キャラでI2Vより忠実という意味ではない。

## 調査根拠・検証の範囲

- [Comfy公式R2V説明](https://docs.comfy.org/tutorials/video/minimax/minimax-h3-native#minimax-h3-reference-to-video-r2v)：
  FL2VAとは別のRef2VA重みを使用し、参照の役割を明示する。
- [MiniMax公式参照プロンプト仕様](https://huggingface.co/MiniMaxAI/MiniMax-H3/blob/main/docs/VIDEO_PROMPT_WRITING_GUIDE_ref_en.md)：
  外見の参照をSubjectとして定義し、画面の開始アンカーと区別する。
- [固定ComfyUI実装](https://github.com/Comfy-Org/ComfyUI/blob/73c9bad4d21e7addbe1d13bc92eee0f1431b017d/comfy_extras/nodes_minimax_h3.py)：
  native R2Vの参照入力・max/match・17k+5・AV latentを利用。独自の生成コアへ差し替えない。
- [単一5090の実験記録](https://github.com/yuichi-suzuki-highdrama/minimax-h3-local-pipeline-notes)：
  参照サイズの画質/速度トレードオフを示す参考報告。別環境の速度や画質を保証するベンチマークではない。

自動テストはプロンプト/尺連動、参照上限、モデル依存、リンク両端、モデル退避/出力順、
ノードとグループの非重複、再生成一致、起動時manifest統合を検査します。
Docker buildはノードimportと両モードのネットワーク前entrypoint smokeを実行します。
これらは実GPUでの動画生成・連続2回の生成・キャラ保持の目視確認の代わりにはなりません。
現時点で生成品質の実機ベンチマークは付属していません。
